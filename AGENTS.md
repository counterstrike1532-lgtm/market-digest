## 0. Первое, что нужно сделать в любой сессии

Прежде чем писать хоть строку кода:

1. `git log --oneline -10`
2. `git status -sb`
3. `git log origin/master..HEAD --oneline` — что лежит локально и не запушено
4. Полный прогон тестов (`pytest -q`), назвать **число** прошедших тестов
5. Прочитать `CLAUDE.md` и последний файл `docs/HANDOFF_*.md`

Разведка — не формальность. Локальные незапушенные коммиты в этом репозитории
уже приводили к тому, что боевой прогон шёл на старом коде, а правку считали
непроверенной ещё сутки. Всегда выясняй, что реально работает в продакшене.

Если фактическое состояние репозитория расходится с тем, что написано ниже
(раздел «Текущее состояние»), — **верить репозиторию, а не этому файлу**, и
сказать владельцу о расхождении.

## 1. Что это за проект

`market-digest` — личный пайплайн одного человека, не продукт и не стартап.

Каждое утро в будни (GitHub Actions cron, ~5:17 UTC) он:

1. собирает польские и международные финансовые новости из ~21 RSS-ленты;
2. тянет числовые данные (NBP, stooq, yfinance как фолбэк, Eurostat);
3. через Gemini ранжирует сюжеты (`RANK_PROMPT`) и пишет 2 черновика
   LinkedIn-постов (`DRAFT_PROMPT`): digest и single;
4. верифицирует числа в черновиках против текстов источников (`verify.py`);
5. рисует график (matplotlib);
6. отправляет всё это в Telegram-канал.

Три цели проекта, в порядке важности для владельца:

- **утренний брифинг для себя** — он это реально читает каждый день;
- **материал для LinkedIn** — публикуется **вручную**, не каждый день,
  и только после личной вычитки;
- **инженерное портфолио** — код смотрят люди, поэтому история коммитов
  и чистота диффов имеют значение.

Владелец — Danylo, второй курс Finance & Accounting, Kozminski University,
Варшава, цель — IB/AM. Общение по-русски, неформально, коротко.

### Почему это важно понимать

Ошибка в этом проекте не «падает тест» — она **выходит под настоящим именем
в маленькое профессиональное сообщество**. Выдуманное число или неверная
атрибуция источника в опубликованном посте стоит дороже, чем любая
неоптимальность кода. Отсюда все правила ниже про честность вывода.

## 2. Кто принимает решения

**Владелец — единственный, кто решает.** Агент:

- не пушит без явной команды `пуш`;
- не коммитит без явной команды `коммить`;
- не начинает новую задачу, пока предыдущая не принята вручную по живому
  утреннему прогону;
- не выбирает между двумя разумными трактовками требования — **задаёт вопрос**;
- не предлагает новых фич (см. раздел 12 — список отклонённого);
- не «заодно» рефакторит соседний код.

Формула, которая работает в этом репозитории и которую нельзя нарушать:

> **шаг → СТОП → диф текстом → «ок» от владельца → следующий шаг**

Каждый шаг заканчивается явным словом «СТОП» в отчёте. Не объединяй шаги,
даже если они «очевидно связаны». Именно этот режим ловил ошибки, которые
иначе уехали бы в коммит.

Эти вещи агент **не меняет** ни при каких обстоятельствах, даже если видит

- любые секреты: `GEMINI_API_KEY`, токен и chat_id Телеграма, ключ FRED.
  Не печатать в лог, не коммитить, не переносить в код, не подставлять
  в тесты. Они живут в GitHub Secrets и локальном `.env`.
- `.gitignore` — не редактировать по своей инициативе.
- workflow-файлы GitHub Actions (расписание cron, права) — только по явной задаче.
- `state/` — не трогать и не коммитить руками. `state/seen.json` и

коммит с изменениями кода.

## 4. Git-дисциплина

Правила выстраданы, а не эстетические.

- **`git add -A` запрещён навсегда.** В рабочем дереве постоянно лежат
  незатреканные рабочие документы (`docs/*`, черновики, распечатки диффов),
  и `add -A` затягивает их в коммит. Использовать явный список файлов или
  `git add -p`.
- При `git add -p` на файле с несколькими независимыми хунками —
  **обязательно** `git diff --cached --stat` перед каждым коммитом и показать
  вывод владельцу.
- **Один коммит — одно логическое изменение.** Не смешивать несвязанные
  правки даже внутри одного файла.
- Код и промпты — **разные коммиты**, всегда.
- Push только по отдельной явной команде. Никогда не в той же сессии
  автоматически «раз уж закоммитили».
- Не больше **2–3 изолированных правок за сессию**. Иначе при утренней
  приёмке невозможно понять, какая правка сработала, а какая сломала.
- Сообщения коммитов — **по-русски, кириллицей**. Не транслитерировать в
  латиницу. (Правило про латиницу существует только для `.ps1`-скриптов
  и к коммитам не относится — предыдущий агент это путал.)
- В теле коммита — только описание изменения. **Никаких комментариев из чата**,
  никаких «как обсуждали», никаких эмодзи и подписей агента.
- Ветка одна: `master`. Репозиторий: `counterstrike1532-lgtm/market-digest`.
- Ничего не удалять из рабочего дерева самостоятельно (включая `diff.txt`,
  `docs/*`, `__pycache__`) — сообщить владельцу и ждать решения.
- **История линейная, merge-коммитов не делаем.** Если локальный `master`
  отстал от `origin/master` на автокоммит бота (`state/seen.json` +
  `state/metrics.json` из ночного прогона) — `git rebase origin/master`,
  не `git merge`. Файлы не пересекаются, конфликтов быть не должно.

### Отдельно про Antigravity

- Артефакты самого агента (walkthrough-файлы, планы, отчёты, кэш IDE)
  **не коммитить**. Если инструмент создаёт их в рабочем дереве — сказать
  владельцу, чтобы он добавил их в `.gitignore` сам.
- Не запускать несколько агентов параллельно на одном рабочем дереве.
  Параллельные агенты ломают правило «одно изменение за раз» и делают
  невозможной атрибуцию поломки.
- Автономный режим/auto-run для `git commit`, `git push`, `rm`, установки
  зависимостей и сетевых вызовов — **выключить**. Эти команды выполняются
  только после подтверждения человеком.
- Не использовать браузерную автоматизацию для чего-либо, связанного
  с LinkedIn (см. раздел 12).

## 5. Тесты

- Фреймворк: `pytest`. CI — GitHub Actions.
- **Актуальное число тестов сверять прогоном**, а не по этому файлу.
  На момент написания было 233 зелёных.
- `pytest` живёт в `requirements-dev.txt`, а не в `requirements.txt` —
  `setup.ps1` его не ставит, это типичная ловушка для системного `python`.
- Перед любой правкой — прогон. После правки — прогон. Называть число в отчёте.
- **Ни одного живого вызова Gemini из тестов.** Переменная
  `NEWSBOT_ALLOW_LIVE=1` — это гард; в тестах она не ставится никогда.
- Новых зависимостей не добавлять. Новых источников данных не добавлять.
- **Никогда не подгонять продакшен-код под тестовую фикстуру.** Был прецедент:
  агент добавил чёрный список в боевой код, чтобы прошёл тест. Правильно —
  чинить фикстуру. Если тест не проходит, потому что фикстура не отражает
  реальность, скажи об этом, а не обходи.
- Негативные ассерты должны быть сильными. `assert "nan" not in rendered` —
  хорошо; `assert result is not None` при проверке отсутствия мусора — слабо.

## 7. Принципы кода, которые нельзя нарушать

### 7.1. Явный сигнал вместо тихой потери

> **Если что-то не разобралось, не совпало, не нашлось — это должно быть видно
> в выходном сообщении, а не исчезать.**

Самые дорогие баги в этом проекте выглядели как успех. Значок `✅ 1/1`
стоял два утра подряд рядом с черновиком, где из четырёх чисел сверено было
одно: остальные три не распарсились и молча выпали из знаменателя.

Из этого следует:

- непарсящаяся пара всё равно попадает в знаменатель — со статусом `UNPARSED`;
- пустое ядро числа возвращает `[]`, а не `[""]` (`text.find("")` всегда даёт 0
  и ложно засчитывается как найденное совпадение — это была настоящая мина);
- если источник не догрузился, в сообщении появляется строка об этом, а не
  тишина.

### 7.2. Отсутствие данных называется отсутствием данных

Обратная сторона того же принципа: `+nan%` — это потеря, которая видна,
но в виде мусора, а не сигнала. Если значение не число (`None`, `nan`) —
печатать «нет данных», а не процент. Никогда не подставлять ноль вместо
отсутствующего значения.

### 7.3. Сознательное дублирование иногда правильно

Функция `_is_number` (`src/main.py:181` и `src/numbers.py:21`) и выражение
`no_figures_declared` (`src/main.py:410` и `src/verify.py:755`) **намеренно
продублированы** в разных файлах, а не вынесены в общий `utils.py`. Причины:
направление импортов и нежелание городить преждевременную абстракцию.
В докстрингах/комментариях написано, что они должны меняться вместе.

**Не «исправляй» это.** Если видишь дублирование — сначала проверь докстринг:
возможно, оно объяснено и одобрено.

### 7.4. То, что вне охвата, — решение, а не TODO

Если что-то сознательно не покрывается текущей итерацией (например,
двусловные квалификаторы `more than`, `up to`, `at least` в парсере чисел) —
это формулируется в докстринге как **сознательное решение**, а не как `TODO`.
`TODO` порождает ощущение недоделки; явная фиксация границы — нет.

### 7.5. Не расширять регексы «на всякий случай»

Расширение регексов (например, `_STORY_NUM_RE`) откладывается до тех пор,
пока не накопится частотная статистика по живым прогонам. Не угадывать,
какие формы встретятся.

## 8. Что делает верификатор и почему это чувствительно

Верификатор сверяет числа из черновика с текстами загруженных источников
и выставляет вердикт. Ключевые инварианты, которые нельзя сломать:

- знаменатель совпадает с количеством пар в блоке `FIGURES`;
- `✅` не ставится, если найдено не всё;
- есть отдельная ветка для случая «найдено больше нуля, но меньше всех» —
  она достижима, потому что FRESH DATA матчится через `data_text` в обход
  `bodies`, а `combined_body` общий на весь черновик, а не per-pair;
- порядок веток в `render_draft_message` (`src/main.py:329`) — **два уровня,
  не один.** Верхний уровень проверяет первыми:
  1. `block.get("_parse_failed")` → «FIGURES не распарсился»;
  2. `elif block.get("_verify_unavailable")` → «числа не верифицированы»
     (verify.verify_drafts упал целиком).

  Только после них идёт `else` — это отдельный, вложенный уровень: внутри
  него ещё пять подветок: `offending непуст` → `denom == 0` →
  `found == denom` (✅) → `found == 0` → `0 < found < denom`. Новую ветку
  добавлять с пониманием, на какой из двух уровней она относится — верхний
  (ранняя проверка формата/доступности) или вложенный (разбор вердикта).

  Отдельно и независимо от всего вышеперечисленного — блок футера
  «источники:» (T15, `src/main.py:409-427`), который печатается всегда и не
  исчезает ни при каком входе (раздел 7.1). У него свои 4 подветки: цифр не
  заявлено / не распознаны / несуществующие номера сюжетов / валидные
  сюжеты.

**Alarm fatigue — известный риск, но не повод откатываться.** Если `MAYBE`
встаёт вообще на всём — это отдельный сигнал к разбору, а не признак того,
что верификатор сломан. Картина стала честной. Реагировать не раньше, чем
накопится несколько дней наблюдений.

## 9. Правки промптов — отдельная дисциплина

Изменения `DRAFT_PROMPT` делает **только владелец** или агент по прямому
поимённому указанию. Правила:

- **Одна правка `DRAFT_PROMPT` в день.** Больше — и невозможно понять,
  какая сработала и чем модель компенсировала запрет.
- Правка вносится только если проблема встречалась **минимум дважды**.
  Одноразовая странность записывается в наблюдения и ждёт повтора.
- **Если запрет конфликтует с другой инструкцией — убрать конфликтующую
  инструкцию, а не наслаивать сверху ещё один запрет.** Именно так был
  вылечен повторяющийся «указательный» зачин.
- Запрещать **классы** проблем («ложная мгновенная причинность»), а не
  конкретные слова. Запрет слова модель обходит синонимом.
- **BAD-примеры работают лучше абстрактных правил** для стилевых проблем.
  GOOD-примеры брать из реальных удачных фраз живых черновиков.
- После каждого запрета смотреть, **чем модель его заполнила**. Компенсация —
  самое интересное, что происходит после запрета.
- Задавать тон прилагательными («живо», «неформально») бесполезно — это то,
  что модель выполняет хуже всего. Работают примеры и запреты конструкций.

## 10. Стилевые проблемы черновиков — активный список

Не задача агента их чинить самостоятельно, но нужно знать, что это
отслеживается и что «улучшить промпт» — не самостоятельная инициатива.

Рамка постов: **«начитанный активный студент», не аналитик.** Тест поста —
сможет ли владелец сам ответить на первый уточняющий вопрос в комментариях.

Активные рецидивы:

- **закрывающее предложение-обобщение** (запрещено, повторялось 5+ раз);
- **предложение-указатель в зачине** (корневая причина найдена и устранена);
- **отсутствие первого лица** (5+ дней подряд, текст от этого стерильный);
- **ложная атрибуция источника** (3+ случая);
- протечка формулировок формы в текст («The common view is that»,
  «Two numbers stand out»);
- невытягиваемый вопрос в конце;
- дословно скопированные примеры из промпта (привычка `3.1-flash-lite`);
- абстрактные существительные вместо конкретной детали.

## 12. Отклонено ранее и не обсуждается

Не предлагать. Если кажется, что это хорошая идея, — оно уже рассматривалось
и было отклонено осознанно:

Не предлагать переписать проект на другой стек, не вводить асинхронность,
не менять формат Telegram-сообщений «для красоты», не добавлять веб-интерфейс.

## 13. Ошибки предыдущего агента — не повторять

Документированные поведенческие сбои, каждый стоил времени:

1. **Транслитерация кириллических сообщений коммитов в латиницу** — правило
   про латиницу относилось только к `.ps1`-файлам и было применено не по адресу.
2. **Комментарии из чата в теле коммита** — тело коммита описывает изменение,
   и только его.
3. **Диф отдавался ссылкой на вывод инструмента вместо текста в теле
   сообщения.** Нарушалось многократно. Владелец видит только текст сообщения.
   **Диф присылать текстом.** Если он длинный — присылать по частям, но текстом.
4. **Обновление внешнего индекса памяти после формального завершения сессии** —
   сессия закончена значит закончена.
5. **Добавление чёрного списка в боевой код ради прохождения фикстуры.**

## 14. Чек-лист перед каждым коммитом

Выполнять пунктами и показывать результат, а не писать «проверил».

1. Полный прогон тестов, назвать число.
2. `git diff --cached --stat` — показать вывод.
3. Построчно подтвердить по дифу, что `RANK_PROMPT`, `DRAFT_PROMPT`,
   TONE CEILING и правило NUMBERS **не изменены**. Не «я не трогал», а
   результат проверки диффа.
4. Проверить, не попал ли в стейдж мусор: `diff.txt`, `docs/*`, `__pycache__`,
   артефакты IDE, `.env`. Ничего не удалять самому — сообщить.
5. Перечислить, что было замечено, но **не** починено (см. раздел 15).
6. СТОП. Коммит — только после слова «коммить».

## 15. Формат отчёта по шагу

```
ШАГ N — <что сделано>

ДИФ (текстом, целиком):
<...>

ТЕСТЫ: <число> прошло, <число> упало

ЗАМЕЧЕНО, НО НЕ ПОЧИНЕНО:
- <...>

ВОПРОСЫ:
- <...>

СТОП.
```

Раздел «замечено, но не починено» обязателен. Если по ходу работы видишь
другую поломку — **записываешь, но не чинишь**. Смешение задач ломает
атрибуцию.

Раздел «вопросы» — там, где требование допускает две трактовки. Вопрос
всегда лучше догадки, даже если догадка кажется очевидной.

## 17. Короткая версия, если читать некогда

1. Сначала разведка, потом СТОП, потом ждать команды.
2. Не трогать `RANK_PROMPT`, `DRAFT_PROMPT`, TONE CEILING, NUMBERS, секреты.
3. `git add -A` запрещён. Коммит и пуш — только по явной команде.
4. Один коммит — одно изменение. 2–3 правки за сессию максимум.
5. Диф — **текстом в сообщении**, не ссылкой на инструмент.
6. Тихая потеря данных — худший баг. Всё непонятое должно быть видно в выводе.
7. Вопрос вместо догадки.
8. Ничего не чинить «заодно». Записал — и дальше по задаче.
9. Не предлагать фичи из раздела 12.
10. Тест не проходит — чинить фикстуру, а не подгонять боевой код.
