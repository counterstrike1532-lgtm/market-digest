# OVERVIEW — описание проекта для внешнего ревью

Документ для эксперта, который видит проект впервые и должен оценить архитектуру и
предложить улучшения. Написан так, чтобы не требовать чтения кода. Состояние на
30.07.2026, репозиторий публичный: `github.com/counterstrike1532-lgtm/market-digest`.

---

## 1. Что это и зачем

Полностью автоматический бот: каждое будничное утро собирает финансовые новости
(Польша, США, рынки, ИИ), отбирает из них содержательные сюжеты, подтягивает к ним
свежие цифры из официальных источников (курсы NBP, индексы, инфляция Eurostat) и
присылает всё это в Telegram вместе с тремя черновиками постов для LinkedIn.
Владелец — студент 2 курса Finance & Accounting (Kozminski University, Варшава),
цель — попасть в investment banking / asset management. Основная польза бота —
не посты, а то, что владелец приходит на собеседование уже в курсе рынков; черновики
постов — побочный продукт. Стек полностью бесплатный: только free-tier API и
GitHub Actions на публичном репозитории.

## 2. Пайплайн по шагам

Оркестрация — `src/main.py:main()`. Реальные числа взяты из боевых прогонов
(см. `CLAUDE.md`, `docs/HANDOFF.md`).

| # | Шаг | Файл | Вход → выход |
|---|-----|------|---------------|
| 1 | Сбор | `src/collect.py::collect_all` | 21 RSS-фид + Hacker News (Algolia API) + Reddit (`.json`, обычно 403 с датацентровых IP — норма) → ~280 записей/сутки |
| 2 | Дедуп | `collect.py::collect_all` внутри | сначала по нормализованной ссылке, потом `dedupe_by_title` по пересечению значимых слов заголовка (ловит один сюжет из разных изданий, до ~40% записей — дубли) |
| 3 | Фильтр «уже видели» | `main.py::load_seen` | сюжеты, показанные за последние 21 день, отбрасываются |
| 4 | Фильтр свежести | `main.py::filter_by_age` | догляд поверх `--hours` (по умолчанию 26 ч на сбор): запись старше `freshness.max_age_days` (по умолчанию 7) из конфига отбрасывается; запись без даты публикации не отбрасывается никогда, только помечается |
| 5 | Цифры | `src/numbers.py::gather` | NBP FX (PLN/USD, PLN/EUR, PLN/CHF + Δ30д), stooq (WIG20, S&P 500, Nasdaq, дневные CSV), Eurostat HICP (PL/DE/EA19, годовая инфляция), FRED — опционально, ключ не заведён |
| 6 | График рынков | `src/charts.py::market_overview` | matplotlib, WIG20 vs S&P 500 за 45 дней к 100, PNG в Telegram фото ДО текстовой сводки — 0 запросов LLM |
| 7 | Эвристический предотбор | `main.py::heuristic_prefilter` | без LLM: score = weight·2 + бонус за официальный тег + свежесть + log-социальный вес, топ-100 |
| 8 | **Отбор — Gemini #1** | `src/brain.py::rank` | ОДИН запрос на весь список (RANK_PROMPT), топ-12 сюжетов с оценкой 0-10 и углом |
| 9 | Догрузка текста статей | `src/enrich.py::enrich` | полный текст для топ-6 сюжетов (regex-парсинг HTML, без bs4); Google News-ссылки не догружаются намеренно (редирект-обёртка); пейволлы (Axios, MarketWatch) падают молча |
| 10 | **Черновики — Gemini #2** | `src/brain.py::draft` | ОДИН запрос (DRAFT_PROMPT) → фиксированно 3 черновика: digest (120-170 слов), digest-short (80-110), single (110-170) + у каждого свой VERDICT/WHY/CHECK_FIRST |
| 11 | График из FIGURES | `src/charts.py::figures_chart` | только если у черновика 1 распознались 2-5 чисел одной единицы измерения с источником |
| 12 | **Верификация цифр** | `src/verify.py::verify_drafts` | уровень a — без LLM, посимвольная проверка числа в тексте статьи или в блоке FRESH DATA; уровень b — **Gemini #3, условно**, только если есть черновик с его собственным VERDICT POST/MAYBE и числом со статусом FOUND — ловит подмену контекста |
| 13 | Доставка | `src/deliver.py` | Telegram: `sendPhoto` (график рынков) → `sendMessage` кусками по ≤3900 симв. → `sendPhoto` (график к черновику 1) |
| 14 | Запоминание | `main.py::save_seen` + workflow | `state/seen.json` коммитится обратно в репозиторий самим GitHub Actions job |

Итог по расходу LLM: 2 запроса в обычный день, 3 — если верификатору есть что
контекстно проверять. Бюджет квоты см. раздел 6.

## 3. Ключевые инженерные решения и почему

Это раздел, ради которого стоит читать документ — большинство решений здесь не
очевидны из кода без объяснения мотива.

**Вся архитектура собрана вокруг лимита Gemini free tier — 20 запросов В СУТКИ на
модель.** Не токенов, не минутного лимита — именно запросов в день. Поэтому отбор
сюжетов (`rank`) и генерация черновиков (`draft`) — каждый ровно ОДИН вызов на весь
список, а не батчи по N штук с паузами. Вход в 1M-токенное окно контекста Gemini
спокойно тянет сотню заголовков разом, так что дробить нечего. Эвристический
предотбор до 100 сюжетов (шаг 7) существует не из-за лимита токенов, а чтобы держать
промпт компактным и прогон — быстрым. Верификация цифр (шаг 12, уровень b) — тоже
один запрос на ВЕСЬ прогон сразу по всем спорным числам во всех черновиках, не по
одному на черновик.

**Каскад моделей с памятью дневного исчерпания.** `GEMINI_MODEL` задаёт список
моделей через запятую (`gemini-3.5-flash,gemini-3.6-flash,gemini-3.1-flash-lite`),
`brain._call` перебирает их по очереди. Критично: HTTP 429 бывает двух разных видов,
и их нельзя путать. 429 с `"PerDay"` в теле ответа значит дневная квота ИМЕННО ЭТОЙ
модели кончилась до сброса (~09:00-10:00 UTC) — ждать бессмысленно, код сразу
переходит к следующей модели и запоминает это в `_day_exhausted`, чтобы больше не
пытаться. Обычный 429 (per-minute) — временный всплеск, и здесь как раз нужен
экспоненциальный backoff. Перепутать эти два случая — либо впустую ждать модель,
которая не ответит часами, либо сдаться слишком рано на временном лимите.

**400 — детерминированная ошибка, не ретраится тем же телом.** Если Gemini вернула
400, следующий идентичный запрос вернёт то же самое. Вместо повтора код по одному
снимает параметры, которые могли вызвать ошибку (`thinkingConfig`, затем
`responseMimeType`), логирует тело ответа и только потом переходит к следующей
модели. Отдельно: моделям `gemini-3*` нельзя слать `thinkingConfig.thinkingBudget: 0`
— гарантированный 400.

**Верификатор — принципиально НЕ редактор.** `src/verify.py` находит проблемы
(число не найдено в тексте, число найдено, но контекст не совпадает), но никогда
не переписывает и не удаляет ни одного символа из текста, который написала модель.
Два явных обоснования: (1) модель, которая ошиблась при извлечении числа в первый
раз, не имеет особого преимущества, чтобы поймать свою же ошибку при повторном
проходе — «исправление» просто маскирует ошибку ложной уверенностью; (2) молчаливая
автокоррекция убирает последнюю линию обороны — глаза владельца перед публикацией.
Вместо правки — под каждым черновиком строка `ЦИФРЫ: ✅/⚠️/❌` и, если нужно, явная
пометка «VERDICT эффективно MAYBE», не трогающая исходную строку VERDICT.

**Различение «цифр нет» и «не распарсилось».** `charts.parse_figures` возвращает
`None`, только если поле FIGURES пустое или буквально `"none used"` — это
единственный законный случай «цифр нет». Если текст непустой, но ни одна пара
«число → источник» не распозналась, возвращается `[]` (пусто, но не `None`) —
осознанно другое значение. Это разделение появилось не из абстрактной
осторожности: в процессе разработки реальный баг именно тут дал ложный ✅ на
черновике, где числа физически были, просто в незнакомом парсеру формате. Ложное
«всё проверено» хуже отсутствия проверки вообще, потому что усыпляет бдительность.

**Эвристический предотбор без LLM** — единственный способ уместить отбор в один
запрос вне зависимости от того, сколько сюжетов собралось за день (280 сегодня,
может быть 500 завтра). Скор считается по весу источника, бонусу за официальный тег
(`poland_official`, `us_official`, `ai_primary`), свежести и логарифму социального
веса (HN points / Reddit score) — простая, читаемая формула, не ML.

**`state/seen.json` коммитится ботом из самого workflow.** Это не только защита от
повторной публикации сюжета (21 день памяти), но и побочный эффект: у запланированных
GitHub Actions workflow есть авто-отключение после 60 дней без единого коммита в
репозиторий. Ежедневный коммит `state/seen.json` эту проблему снимает сам, без
отдельного heartbeat-задания.

**Калибровка промптов — результат прямых указаний владельца, не абстрактного
«качества».** Рамка «начитанный активный студент», не аналитик — снижает
репутационный риск и честно описывает, чем черновики являются на самом деле.
TONE CEILING — запрет на языковые обороты уровня банковской записки, которые
студент 2 курса не произнёс бы вслух. Запрет на выдуманное первое лицо («я следил
за этим фондом недели») — по прямому указанию владельца строже, чем запрет на
выдуманную цифру: цифру можно перепроверить по источнику, а придуманное участие
самого автора — нет, и это обходится дороже при разоблачении. Полякоцентричный
скоринг в RANK_PROMPT (сюжет с польским/CEE углом обязан обгонять равный по
качеству абстрактный глобальный) — единственное структурное преимущество, которое
у бота реально есть: владелец читает GUS/NBP на польском в день выхода, обычный
finance-контент-бот такого не даёт.

## 4. Ограничения среды, которые сформировали код

- **Windows 11 / PowerShell 5.1 / cp1251.** PowerShell 5.1 без BOM читает `.ps1` и
  `.cmd` как cp1251 — любая кириллица в этих файлах ломает парсер целиком. Поэтому
  `run.ps1`, `setup.ps1`, `digest.cmd` — строго ASCII, все сообщения в них
  по-английски, хотя вся остальная коммуникация по проекту — по-русски.
- **`encoding="utf-8"` обязателен в каждом `open()`/`read_text()`/`write_text()`.**
  Системная кодировка владельца — cp1251; без явного аргумента чтение
  `config/sources.yaml` (кириллица в комментариях) или `state/seen.json` падает.
  Это не проверяется линтером — только код-ревью.
- **Репозиторий публичный намеренно.** Квота минут GitHub Actions на приватных
  репозиториях владельца уже занята другим его ботом; публичный репозиторий получает
  отдельный, практически неограниченный для этой нагрузки пул минут. Следствие:
  в репозитории не может быть ничего чувствительного — секреты только через
  GitHub Secrets (в Actions) и `secrets.ps1` (локально, в `.gitignore`, отсутствие
  в истории git проверено).
- **Пейволлы не обходятся.** `enrich.py` не имеет и не планирует обходной логики
  для Axios/MarketWatch — просто не получает текст, история идёт без чисел.
- **Reddit 403 почти всегда** с датацентровых IP (в т.ч. GitHub Actions) — принято
  как норма, не расследуется: RSS и так даёт ~280 записей на 8 отобранных, Reddit
  не критичен.
- **stooq.pl — анти-бот на голый запрос.** Дефолтный/нехарактерный User-Agent
  получает HTML-заглушку "This site requires JavaScript" вместо CSV. Починено
  браузерным UA/Accept, но это по определению хрупко (см. раздел 5).

## 5. Известные слабые места и незакрытые хвосты

Честно, без приукрашивания:

- **Зависимость от одного бесплатного LLM-провайдера.** Весь отбор, генерация и
  верификация живут на Gemini free tier. Если Google изменит условия free tier,
  имена моделей или поведение лимитов (уже случалось: `gemini-2.5` у этого ключа
  перестала работать), пайплайн просто останавливается до ручного обновления
  списка моделей. Альтернативного провайдера как фолбэка нет.
- **Даты публикации RSS принимаются на веру, не проверяются независимо.** И
  внутренний `--hours`-фильтр в `collect.py`, и отдельный `filter_by_age` в
  `main.py` защищают только от ОТСУТСТВУЮЩЕЙ даты (тогда запись помечается и не
  отбрасывается). Фид, который отдаёт НЕВЕРНУЮ, но синтаксически валидную дату,
  пройдёт оба фильтра незамеченным.
- **Лаг публикации Eurostat HICP.** Даже после исправления бага декодирования
  JSON-stat (число и период больше не путаются между странами), сама цифра
  по построению отстаёт на 1-2+ месяца от календарной даты. Маркер `— старше N
  мес!` — это честная маркировка, а не устранение лага.
- **`gemini-3.1-flash-lite` как последний фолбэк заметно слабее** в аналитической
  глубине, которую требуют RANK_PROMPT/DRAFT_PROMPT. Это страховка от полного
  исчерпания квоты, а не равноценная замена — в дни, когда реально используется
  именно она, качество дайджеста вероятно проседает без явного сигнала об этом.
- **`style/my_posts.md` — пустой шаблон.** Самый ценный источник персонализации
  (голос именно этого автора) ещё не наполнен ни одним реальным постом — черновики
  сейчас следуют только общим правилам голоса из промпта, не реальной манере
  владельца.
- **FRED не подключён.** Код (`fred_series`) есть, `FRED_API_KEY` не заведён —
  блок данных по ставке ФРС/US CPI/безработице молча отсутствует в каждом прогоне.
- **Расписание GitHub Actions плавает.** Крон может сдвинуться на 5-20 минут или
  иногда пропустить прогон — это особенность платформы, отдельно не решается.
- **Тестов в привычном смысле нет.** Нет каталога `tests/`, нет шага CI на тесты.
  «Тестирование» — это ручной просмотр вывода `--dry` владельцем; это осознанное
  решение владельца (юнит-тесты с моками ему не нужны), но у него есть цена: баги
  вроде найденных в этой сессии (регрессия сбора stooq, ложный ✅ верификатора,
  сдвиг вставки строки ЦИФРЫ, некорректный счётчик квоты) обнаруживаются только
  после боевого прогона, тратящего реальную квоту.

Сознательно НЕ сделано (не забыто, а решение):

- **Twitter/X-коллектор** отложен: материала и так избыток (280 записей/сутки на
  8 отобранных), а скрапинг требует поддерживаемого burner-аккаунта ради
  маргинальной выгоды.
- **Автопостинг в LinkedIn не планируется.** Черновики — всегда отправная точка
  для человека, не публикационный конвейер. Это ценностное решение владельца
  (контроль качества и репутационный риск важнее автоматизации), не техническое
  ограничение.
- **Платный уровень LLM не рассматривается** — жёсткое требование владельца
  «только бесплатное», а не вопрос технической возможности.

## 6. Цифры расхода

- **Gemini-запросы за прогон:** 2 обычно (отбор + черновики), 3 — если сработал
  уровень b верификатора. Потолок — 20 запросов/сутки на модель, 3 модели в
  каскаде дают формальный запас до 60/сутки суммарно, хотя ежедневный плановый
  прогон использует лишь малую часть этого запаса.
- **Время прогона:** нигде явно не логируется и не измеряется в коде — это стоит
  отметить эксперту отдельно. Единственный ориентир — `timeout-minutes: 20` в
  workflow как верхняя граница; реальные прогоны в неё укладываются.
- **Деньги:** $0. Все источники данных (NBP, stooq, Eurostat, HN Algolia, Reddit
  `.json`, RSS) бесплатны, Gemini — free tier, GitHub Actions — бесплатный пул
  минут публичного репозитория.

## Вопросы, по которым хотим мнение эксперта

1. **Приоритизация источников.** Из 21 RSS-фида часть явно даёт больше проходящих
   отбор сюжетов, чем другие. Стоит ли формализовать это (например, скользящее
   окно «доля сюжетов от источника, прошедших отбор Gemini за последние N дней»)
   вместо статичных весов в `config/sources.yaml`, выставленных вручную?
2. **Оправдан ли платный tier LLM** хотя бы частично — например, только для
   верификации (уровень b) или как страховка вместо `gemini-3.1-flash-lite» в дни
   исчерпания квоты? При каком объёме использования это окупается по сравнению
   с текущим качественным провалом на слабой модели?
3. **Альтернативы stooq** для WIG20/S&P 500/Nasdaq. Учитывая, что stooq уже
   потребовал обхода анти-бота один раз, есть ли более стабильный бесплатный
   источник дневных котировок с той же простотой интеграции (CSV без ключа)?
4. **Метрики качества черновиков во времени.** Сейчас качество оценивается
   разово, глазами владельца, через `--dry`. Есть ли способ дёшево (без
   дополнительных LLM-запросов) отслеживать деградацию/улучшение качества
   черновиков и точность верификатора на длинном горизонте — например, по доле
   VERDICT POST против MAYBE/SKIP или по частоте срабатывания уровня a?
