## 3. Три поломки, найденные 03.08

Все три одного класса: **тихая потеря вместо явного сигнала.** Чинит T14b.

1. **Причина А.** `charts._NUM_CORE` требует, чтобы value начинался с цифры
   или `$`. Модель пишет `over 67 days`, `four days longer`,
   `seven residential buildings` — такие пары `parse_figures` не распознаёт
   вообще, они не попадают в знаменатель ни с каким статусом.
   Живой лог 08:41: под DRAFT 1 напечатано `✅ verified (1/1 found)` при
   четырёх реально написанных цифрах.
2. **Мина, которую активирует фикс причины А.** `_core_number_variants` при
   пустом числовом ядре отдаёт `[""]`, а не `[]`. `"".find(v)` всегда даёт 0
   — пустой вариант «находится» в начале любого текста. Сегодня безопасно
   только потому, что такие пары до этого кода не доходят. Чинить вместе.
3. **Причина Б, финальное звено.** `bodies_for_source` при непойманном номере
   и битом URL возвращает `[]` → все пары `NO_SOURCE_TEXT`. Отчёт в
   `digest.log` честный, но `main.render_draft_message` считает независимо и
   печатает `цифры 0/3 ✅` — зелёная галочка на нуле проверенных чисел, в
   тексте, который читается перед публикацией.

### Требуемое поведение — три изменения

**1. `src/charts.py` — `_NUM_CORE`/`_VALUE` принимает число со словом.**

Value распознаётся, если это: (а) необязательное слово-квалификатор перед
цифровым ядром (`over 67 days`), или (б) числительное словом само по себе как
ядро (`four`, `seven`, …`twelve` — базовый набор простых числительных, не
полный английский nums-to-words).

Явно: это осознанное решение на первую итерацию, **не недоделка**.
`_split_value` по-прежнему требует цифру в начале, так что эти пары уйдут в
UNPARSED через уже существующую проверку `_to_float(value) is None` — не в
FOUND. Задача пункта — не научить их искать, а сделать видимыми: пара в
знаменателе, честно, UNPARSED, без ✅. Зафиксировать это утверждение в
докстринге рядом с изменением, чтобы через месяц никто не прочитал его как
забытый TODO.

**2. `src/verify.py` — `_core_number_variants` никогда не отдаёт пустой
вариант.**

Если числовое ядро не извлеклось (`core == ""`) — возвращать `[]`, не `[""]`.
`_find_first` с пустым списком корректно вернёт `None`, пара пойдёт в
UNPARSED по существующей проверке, а не рискнёт случайным FOUND по
совпадению единицы измерения в произвольном месте тела статьи.

**3. `src/main.py` — `render_draft_message` не печатает ✅, если не всё
найдено.**

Условие галочки — `found == denom` (и `denom > 0`), не просто «offending
пуст». Два разных случая:

- все пары `NO_SOURCE_TEXT` (`found == 0`, offending пуст по конструкции
  `_render()`) → строка буквально:
  `{verdict} · цифры {found}/{denom} — источник не догружен, сверь вручную`
  (пример: `POST · цифры 0/3 — источник не догружен, сверь вручную`)
- есть и найденные, и ненайденные вперемешку (offending непуст) → уже
  существующее поведение с перечислением, **не трогать вообще**.

`NO_SOURCE_TEXT` не входит в `_offending` по замыслу `verify.py` — это не
вина модели, классификацию не меняем. Чинится только на стороне рендера.

### Тесты
