# ТЗ T11 — market-digest

Написано по итогам живого боевого прогона 02.08.2026 (`send`, реальная доставка
в Telegram). Владелец прочитал все сообщения на телефоне и прислал текст
по-сообщениям. Это первая приёмка в реальном чате, не `--dry`.

Базовое состояние: HEAD = origin/master = `58c1078`, 175 тестов зелёных,
T8/T9/T10 приняты.

- **Живые прогоны и любые вызовы Gemini — только по явному разрешению владельца
  на конкретный вызов.** Тесты только на моках. За T10 правило нарушено четыре
  раза, поэтому T11a ниже делает нарушение технически невозможным — и делается

- Приёмка после каждой части, коммит после приёмки.
- RANK_PROMPT не трогать вообще. DRAFT_PROMPT — только там, где ниже сказано

  (`git diff --output=diff.txt -- src/brain.py`, порядок флагов важен).
- Автоисправление чисел запрещено. Верификатор помечает, не редактирует.
- Новых зависимостей нет.
- `.ps1`/`.cmd` — только ASCII. Всё файловое I/O в Python — `encoding="utf-8"`.
- Гипотезы о причинах формулировать как гипотезы и проверять по коду. Ниже
  места, где я не уверен, помечены словом ГИПОТЕЗА — их проверять, а не
  принимать на веру.

Порядок частей: **a → d → c → b → e**. Причина: a — предохранитель, дальше две
дешёвые части с видимым эффектом, потом тяжёлый верификатор, промпт последним,
потому что его смотрит владелец глазами.

## T11a — предохранитель от живых прогонов

**Зачем.** Четыре несанкционированных живых прогона за T10. Просьбами не лечится.

**Что сделать.**

`brain._call` (единственная точка исходящего HTTP к Gemini) в самом начале
проверяет переменную окружения `NEWSBOT_ALLOW_LIVE`. Если она не равна `1` —
поднимает исключение с внятным текстом («живой вызов Gemini заблокирован;
переменная NEWSBOT_ALLOW_LIVE не выставлена»), никакого HTTP не происходит.

- `run.ps1` в режимах `dry`, `send`, `verify`, `models` выставляет
  `NEWSBOT_ALLOW_LIVE=1` перед запуском Python. То есть запуск владельца работает
  как раньше, без изменений в его привычках.
- `run.ps1 test` и `run.ps1 score` (без `--deep`) переменную НЕ выставляют.
- Workflow в Actions выставляет её в шаге запуска.
- Тесты, которые мокают `_call`, не затрагиваются. Добавить один тест: при
  отсутствии переменной `_call` бросает исключение и не делает запроса
  (проверять через мок транспорта, что вызова не было).

**Приёмка.** `pytest` зелёный. `python -c "import brain; brain._call(...)"` без
переменной падает с понятным сообщением.

## T11d — сжатие сводки (рендерер, промпты не трогать)

**Зачем.** Владелец: «текста как-то дофига». Сводка из 8 сюжетов занимает
~35 строк и разрезается чанкером на два сообщения.

**Что сделать в `render_summary`** (RANK_PROMPT не трогать, всё режем на выводе):

1. **Пояснения только у топ-5 сюжетов.** Сюжеты 6+ печатаются как заголовок +
   ссылка, без строки-пояснения. Число 5 вынести константой рядом с функцией.
2. **Предупреждения о недогруженном тексте схлопнуть в одну строку в конце
   блока СЮЖЕТЫ**: `! текст не догружен: 1, 3, 7, 8 — цифры оттуда не проверены`.
   Сейчас это четыре отдельные строки внутри списка, они рвут чтение.
3. **Пояснение обрезать по границе предложения, если длиннее 160 символов**
   (первое предложение целиком; если и оно длиннее — не трогать, обрезка посреди
   мысли хуже длины).

**Чего не делать.** Не менять число сюжетов в отборе (8 — это вход для
черновиков, а не только для глаз). Не трогать блок ЦИФР — три строки по
категориям владелец принял.

**Приёмка.** Тесты на рендерер с фикстурой из живого прогона 02.08: 8 сюжетов,
4 недогруженных. Ожидаемо: 5 пояснений, одна агрегированная строка
предупреждения, суммарная длина блока СЮЖЕТЫ меньше исходной минимум на треть.

## T11c — ссылка SOURCE под черновиком

**Зачем (баг подтверждён живым прогоном).** Под черновиками 1 и 2 напечатано
`www.bankier.pl www.bankier.pl` — дважды один голый домен, и оба — кликабельные
ссылки на **главную страницу** bankier.pl, не на статью. Это T10b req 3
(Story [N] fallback), который в T10 не реализовали.

**Что происходит сейчас (ГИПОТЕЗА, проверить по коду).** Модель написала в SOURCE
голые домены. `build_domain_urls()` корректно исключил bankier.pl из подстановки
(3+ сюжета с этого домена), поэтому `_wrap_bare_domains` его не тронул — но
дальше `_to_html` самостоятельно линкует любой текст, похожий на домен, в
`https://<домен>`. Если это так, то безопасный фикс T10b обходится ниже по
конвейеру. Проверить прежде, чем чинить.

**Что сделать.**

1. **Разрешение через номер сюжета.** У черновика есть FIGURES со ссылками вида
   `Source [N]`. Собрать множество номеров сюжетов, на которые черновик реально
   ссылается, и печатать в SOURCE URL именно этих сюжетов, по одному на сюжет,
   без повторов. Переиспользовать существующие `quoted_source_form` /
   `_offending_source_quotes`.
2. **Если номер сюжета определить не удалось** — печатать голый домен **простым
   текстом, без ссылки**. Ссылка на главную страницу издания хуже, чем её
   отсутствие: она выглядит рабочей и никуда не ведёт.
3. **Дедупликация**: один и тот же URL в SOURCE не печатается дважды.

**Приёмка.** Регрессионный тест на точных данных 02.08: черновик 1 ссылается на
сюжеты 4 и 2 → в SOURCE два разных URL статей bankier.pl, ни одной ссылки на
корень домена, дублей нет. Отдельный тест: неразрешимый домен остаётся текстом.

## T11b — верификатор: единицы измерения и валюты

**Зачем.** Живой прогон дал 0 FOUND из 8 значений во всех трёх черновиках.
Все три сюжета польские, числа в источниках польские: `4,1 mln ton`, `37 mln zł`.
`_to_search_variants` переводит формат числа (разряды, запятая, tys./mln/mld),
но не слово-единицу рядом с ним, поэтому `4.1 million tons` никогда не совпадёт
с `4,1 mln ton`. Итог — MAYBE на всём, то есть alarm fatigue: через неделю
владелец перестанет читать значки, и верификатор пропустит настоящую ошибку.

Побочный эффект того же бага: `figures_chart` рисует только FOUND, значит
единственный график, который имеет смысл публиковать, не рисуется никогда.
Эта часть — предусловие для T11e и для любых осмысленных картинок.

**Что сделать. Не строить полный переводчик единиц** — сопоставлять по разным
осям:

1. **Числовое ядро** ищется как сейчас (английский и польский формат, разряды
   пробелом/НБСП, tys./mln/mld/proc.).
2. **Единица проверяется отдельно, в окне того же предложения**, а не как часть
   искомой строки. Небольшая таблица синонимов, покрывающая живые случаи:
   `tons → ton, ton, tona, tys. ton, mln ton`; `hectares → ha, hektar,
   hektarów`; `PLN → zł, złotych, PLN`; `EUR → euro, EUR, eurо`;
   `million → mln`; `billion → mld`; `thousand → tys.`; `percent → proc., %`.
   Таблица живёт одной структурой рядом с `_to_search_variants`, чтобы её было
   легко расширять по факту следующих прогонов.
3. **Статус FOUND ставится, когда совпало числовое ядро И единица найдена в том
   же предложении.** Если совпало только ядро — статус остаётся MAYBE с текущим
   поведением. Не ослаблять планку: цель — убрать ложные MAYBE, а не наштамповать
   ложных FOUND.
4. Гейт «ближайшее число того же порядка» из T10c сохраняется как есть.

**Отдельно и обязательно проверить перед реализацией (ГИПОТЕЗА).** Тела статей
`enrich.py` не сохраняет, поэтому 0/8 на 100% не доказано именно этой причиной.
Один из пунктов (`1.3 million tons` в черновике 1) похож на собственный расчёт
модели — разницу 4.1 − 2.8/3.2 — и по-честному не обязан встречаться в источнике
дословно. **Первым шагом** добавить в `digest.log` сохранение того фрагмента
исходного текста, в котором верификатор искал (окно вокруг ближайшего
кандидата), — тогда следующий прогон покажет причину, а не догадку. Это дешевле
любого угадывания.

**Приёмка.** Юнит-тесты на синтетических парах «английская форма из черновика —
польская форма из источника», включая все пять живых значений 02.08. Ни одного
вызова Gemini из тестов. Отдельный тест: число совпало, единица в предложении
отсутствует → MAYBE, не FOUND.

## T11e — черновики: минус один, картинки по делу, FIRST PERSON

Три отдельных изменения, но все в одной зоне и с одной приёмкой владельца.

### e.1 Убрать черновик digest-short

**Зачем.** В прогоне 02.08 черновики 1 и 2 — это одни и те же два сюжета, те же
три числа, 136 и 97 слов. Выбор длины владелец делает сам за минуту, выбор темы
— нет. Второй черновик добавляет сообщение и сотню слов, не добавляя решения.

**Что сделать.** DRAFT_PROMPT просит два черновика: `digest` (120-170 слов) и
`single A/B/C` (как сейчас). Нумерация, рендерер, маршрутизация картинок,
metrics.json — привести в соответствие. Проверить, что JSON salvage-парсер и
тесты не завязаны на константу «три».

**Чего не трогать.** TONE CEILING, объясняющая позиция, правило «максимум один
черновик заканчивается вопросом», «все SKIP — валидный исход», секция NUMBERS.
Формат digest и single не меняется.

### e.2 Картинки только по делу

**Зачем.** В прогоне ушли три картинки, каждая — дословный повтор первой фразы
черновика, который владелец уже прочитал строкой выше. Причина: `figures_chart`
возвращает None (нет FOUND, см. T11b), и фикс ревью №2 откатывает это на
`quote_card`. Гарантия «у каждого черновика ровно одна картинка» оказалась
неправильным инвариантом: наличие картинки важнее её осмысленности только на
бумаге.

**Что сделать.**

1. **Откат фикса ревью №2**: отказ `figures_chart` больше не откатывается на
   `quote_card`. Картинки к черновику нет — и сообщения с картинкой нет.
2. **`quote_card` и `stat_card` из конвейера черновиков убрать** (функции в
   `charts.py` оставить, они покрыты тестами и могут пригодиться; вызовы из
   `main.draft_card()` удалить).
3. **Картинка к черновику рисуется, только если `figures_chart` собрал минимум
   два значения со статусом FOUND.** Ноль картинок за прогон — валидный и
   ожидаемый исход, особенно до приёмки T11b.
4. **График рынков из ежедневной отправки убрать.** Владелец: ежедневный график
   не нужен. Отдельно: текущий сравнивает WIG20 **TR** (с дивидендами) с
   **ценовым** S&P 500, +10% против −1.5% — асимметрия баз частично рисует эту
   разницу сама, и сноска в подвале от первого же комментария не спасёт. Код
   `charts.markets_chart` и его тесты не удалять: оставить доступным через
   `run.ps1` по требованию (флаг `-Markets` или отдельный режим — на усмотрение,
   но ASCII в .ps1). Цифры рынков остаются в текстовом блоке ЦИФРЫ, они и есть
   ежедневная ценность.

**Принцип, который здесь фиксируется:** картинка появляется по событию (есть
проверенные числа), а не по расписанию.

### e.3 FIRST PERSON: «I pulled» — та же ложь, что «I compared»

**Зачем.** Черновик 3 начался с `I pulled these two figures from Forte's recent
earnings estimate.` Это почти дословная копия GOOD-примера из промпта (`I pulled
these figures from Statistics Poland`) — у `3.1-flash-lite` подтверждённая
привычка копировать примеры. И по существу это ровно то же ложное утверждение,
которое T10g запрещал в случае `I compared`: цифры вытащила модель, владелец
статью не открывал. T10g убрал один ложный шаблон и оставил второй — а так как
он стал единственным разрешённым, модель ставит его в каждый черновик.

**Что сделать.** В секции FIRST PERSON: первое лицо по умолчанию **не
используется вообще**. Убрать `I pulled these figures from Statistics Poland`
из GOOD — вместо него безличная формулировка того же факта со ссылкой на
источник. Добавить `I pulled these figures from X` в BAD с пояснением: вытащить
цифру из статьи мог кто угодно, включая машину, и читателю это утверждение
проверить нечем.

Владелец дописывает первое лицо руками перед публикацией, если реально сделал
работу. Это правильный дефолт для машины.

**Осторожно.** Секция и так перекошена в запрет: после T10g два GOOD против
четырёх BAD. Убирая последний позитивный пример, легко получить черновики,
где первого лица нет никогда и текст становится стерильным — но это приемлемая
цена, потому что ложное первое лицо стоит дороже. Отдельного действия не нужно,
просто зафиксировать в HANDOFF как то, за чем смотреть.

**Приёмка e.** Дифф DRAFT_PROMPT в `diff.txt`, владелец смотрит глазами до
боевого прогона. Смотреть шапку ханка: смещение номеров строк выдаёт, что выше
есть ещё изменённый кусок.
